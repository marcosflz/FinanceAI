## 0. Resumen ejecutivo

El repo ya tiene una base v2 razonable (CSV de Trade Republic, `raw_rows`, `normalized_events`, `financial_movements`, trazabilidad, reglas y un modo de revisión por tarjetas), pero **la app está a medio migrar y varias piezas críticas no funcionan**:

1. **La clasificación está rota en código**: faltan imports en `src/classify/rules.py`, `src/classify/pipeline.py` y `src/v2_api.py`. Cualquier intento de importar con reglas o clasificar lanza `NameError`.
2. **La base de datos local está en una revisión antigua de Alembic** (`bda3fcb75c3f`). `alembic upgrade head` falla y la tabla `classification_rules` no tiene `auto_aprobar`, por lo que `/api/v2/classification-rules` devuelve 500.
3. **El dashboard, la cartera y Grafana siguen leyendo tablas legacy** (`documentos`/`movimientos`), no el modelo v2. El dashboard muestra 152 movimientos de ene–feb; la bandeja de movimientos muestra 585 de ene–jun. La cartera muestra 0 activos aunque hay 14 en v2.
4. **Las transferencias propias no se detectan**: solo 26 de ~129 se marcan como `transferencia_interna`. La causa principal es que la cuenta de Trade Republic tiene asignado el IBAN de Revolut, los patrones de `accounts.alias_patrones` no se usan y el IBAN se sustituye por `[IBAN]` antes de intentar casarlo.
5. **El coste de importación es alto**: 585 filas tardan ~17 s (13,7 s solo en reglas), por abrir una sesión y hacer commit por cada fila. El pipeline de clasificación hace lo mismo y además escribe el job entero en cada movimiento.
6. **La resiliencia de duplicados es incompleta**: no se detectan duplicados dentro del mismo fichero, el fingerprint puede colapsar repeticiones legítimas y el detector L3 está mal construido.
7. **La UI tiene una base visual decente, pero es híbrida y está sin pulir**: dashboard legacy, 38 errores de lint, tablas con scroll horizontal, filtros que no están en la URL, selects con `color-scheme: dark` incluso en claro, cero toasts/undo, y varias pantallas mono-líticas.

La buena noticia: **con los datos actuales se puede llegar a ~92 % de clasificación automática sin LLM generativo** y dejar el LLM para ~45 filas (unas 20 marcas únicas) por importación semestral.

La arquitectura que encaja con tu idea es de **dos cerebros separados**:

1. **Agente documental** (orquestador local + modelo multimodal vía **OpenCode Go API**) que valida el fichero, extrae texto/tablas, renderiza páginas, hace OCR si hace falta, guarda evidencia (crops/bbox) y produce un `DocumentEnvelope` con hechos, confianza e incidencias.
2. **Decisor tipado Jev** (TypeSafe API) que recibe solo hechos estructurados y responde preguntas atómicas (`choice`/`score`/`noul`) con probabilidades calibradas.

El bucle “LLM + decisor” no debe ser una conversación libre: el orquestador compara la propuesta del agente, las reglas y las probabilidades de Jev; si hay acuerdo y confianza alta, acepta; si no, pide evidencia adicional y repite como máximo 2 veces; si sigue dudoso, va a revisión humana. **Jev no ve PDFs ni imágenes**: su papel es decidir sobre hechos ya extraídos; el multimodal de OpenCode Go es el que mira páginas y crops.

**Matiz:** el Jev tipado es `POST https://api.typesafe.ai/v1/systemone`; no está en OpenRouter ni en OpenCode. OpenCode Go se usa **solo como proveedor de modelos** vía HTTP desde Python (`https://opencode.ai/inference/go/...`), no como agente embebido. **No se usa OpenRouter**: el fallback es otro modelo de Go.

**Orden recomendado:** estabilizar + PostgreSQL + auth (F0) → cuentas/transferencias + reglas (F1) → dedup + PDFs deterministas (F2) → capa de decisión Jev (F3) → agente documental OpenCode Go + bucle de acuerdo (F4) → frontend nuevo + rediseño visual + login (F5) → cartera (F6) → hardening (F7).

**Infraestructura decidida:** PostgreSQL **actual** (pool, `psycopg` v3, Alembic, `pg_dump`); SQLite solo dev/tests forenses. **UI:** se rehace de cero con una interfaz moderna (base neutra, claro/oscuro, acento configurable), Next.js 16 + shadcn/ui + Tailwind 4 + TanStack Query/Table + cliente OpenAPI generado + autenticación email/password.

## 3. Problemas de calidad de datos (con evidencia)

### 3.1 Transferencias y cuentas

- El CSV tiene **209 filas de transferencia**. 104 coinciden con nombres/patrones de cuentas propias (“Marcos Florez Fernandez”, “M. Florez Fernandez”, “Revolut”, “Bunq”, “N26 TOP-UP”). Con una resolución de cuentas correcta, ~129 filas deberían ser `transferencia_interna` (incluye recargas a Revolut/N26).
- Solo 26 están marcadas como internas. El resto se contabiliza como gasto o ingreso, distorsionando ingresos/gastos y ahorro.
- El CSV trae IBAN en `description` en 191 transferencias, pero `counterparty_iban` solo en 82. El parser no extrae el IBAN de `description`; además lo redacta a `[IBAN]` antes de intentar casarlo.
- La cuenta `Trade Republic Default` tiene asignado el IBAN de Revolut. Es un error de seed que invalida la detección.
- `account_id` es NULL en los 585 movimientos, por lo que no se puede calcular el balance neto por cuenta ni conciliar extractos.

### 3.2 Clasificación

- 287 movimientos no tienen ninguna clasificación: 219 gastos y 68 ingresos.
- 178 tienen una `Classification` de broker pero sin `categoria_id`; la UI los muestra como “sin clasificar” aunque el `kind` ya es determinista.
- 163 tarjetas se cubren con las 81 reglas MCC; 61 quedan fuera. Muchas de esas 61 son recargas a Revolut/N26 (deberían ser transferencias internas) o comercios conocidos (Rituals, IKEA, Waylet, Movilidad MMD, PayPal/AliPay, etc.).
- Con una cascada determinista (cuentas + MCC + tipo de transferencia + broker) se puede clasificar ~**540/585 = 92,3 %** sin LLM; el LLM solo necesita ~45 filas, que por marca única son ~20 casos.
- El pipeline actual vuelve a consultar todas las reglas para cada movimiento, abre sesión y hace commit por movimiento; no precompila reglas ni agrupa por merchant.

### 3.3 Duplicados

- Hay 8 grupos de movimientos con misma fecha, importe y merchant. Algunos son claramente legítimos (2 × Bunq test −2 €, 2 × Revolut −2 €). El sistema debe permitir repeticiones legítimas, no colapsarlas.
- El fingerprint no incluye cuenta, contraparte ni ordinal, así que no distingue repeticiones legítimas de duplicados.
- No se detectan duplicados dentro del mismo fichero porque los sets de dedup se cargan antes del bucle y no se actualizan.
- L3 no está detectando bien porque `new_ids` incluye también los movimientos ya vistos en el fichero.

### 3.4 Cartera

- 133 transacciones de activos, 14 activos, pero la UI de cartera lee `activos`/`operaciones` legacy y muestra 0.
- `position_snapshots` tiene una posición negativa (activo 7, −3,08 participaciones) porque el CSV empieza en 2026 y no hay posiciones de apertura.
- `ganancia_realizada` se calcula como `realized_pnl - sell_revenue`, que es el negativo de la ganancia; además no se descuenta el coste de las ventas del coste total.
- `asset_class` conserva los valores del broker (`CRYPTO`, `FUND`, `STOCK`, `MUTUAL_FUND`) en vez del enum propio.
- Los PDFs `extracto_cuenta_valores.pdf` y `extracto_cuenta_cripto.pdf` contienen las posiciones a 06/01/2026 y deberían usarse como apertura.

## 4. Rendimiento: medidas y causas

| Operación | Hoy | Causa principal | Objetivo |
|---|---:|---|---:|
| Import CSV 585 filas | 17,1 s | 585 × `run_rule_for_movement` con sesión + commit (13,7 s); `_recalc_position` por transacción; consultas N+1 | <2 s |
| `classify_pending` 407 sin LLM | 4,1 s | Sesión/commit por movimiento; reglas recargadas; `save_job` por movimiento | <1 s |
| Listado de 100 movimientos | ~200 consultas | `event` y `classification` consultados por cada movimiento | 2–3 consultas |
| Job de clasificación | 2 escrituras + commit por movimiento | `save_job` reescribe log y contadores cada vez | 1 actualización cada 25–50 |
| Recomputar posición | O(n²) | `_recalc_position` recorre todas las transacciones del activo por cada nueva | O(n) por activo |
| PDF (si se añade con LLM por página) | minutos | Llamada LLM por página | <30 s con parser determinista + fallback |

**Cambios concretos de rendimiento:**

1. Precargar reglas una vez por job/import y evaluarlas en memoria. No abrir sesión por movimiento.
2. Una transacción por lote de import; `bulk_save_objects`/`add_all` y un solo `commit`.
3. `save_job` con throttle (cada 25–50 movimientos o 2 s), no por movimiento.
4. `list_movements`: `join`/`selectinload` de `NormalizedEvent` y `Classification` vigente en la consulta principal; DTO sin lazy loads.
5. `_recalc_position`: agrupar por activo y recalcular una vez al final del import; FIFO con lotes.
6. Índices: `(estado, value_date)`, `(account_id, value_date)`, `movement_sources(source_file_id)`, `classifications(movement_id, vigente)` ya existe, `classification_memory(pattern_key, activo)`.
7. PostgreSQL: pool dimensionado, `pool_pre_ping`, índices parciales, `EXPLAIN ANALYZE` de las queries lentas; SQLite solo dev con WAL y `busy_timeout`.
8. Frontend: TanStack Query con cache, virtualización de tabla, no recargar 5 endpoints en cada cambio de filtro, debounce de búsqueda.

## 5. Arquitectura objetivo

### 5.1 Ingesta multi-formato

```
FileProbe (mime, extensión, magic bytes, tamaño)
   │
   ├── CsvAdapter (TR, Revolut CSV, genérico con mapping)
   ├── PdfAdapter (TR statement, Revolut statement, determinista primero)
   ├── ImageAdapter (recibo/foto/screenshot → OCR + visión)
   ├── XlsxAdapter (opcional)
   ├── OfxQifAdapter (opcional)
   └── JsonAdapter (API/broker)
        │
        ▼
DocumentIntakeAgent (tools + multimodal OpenCode Go)  ← solo si hace falta
        │  DocumentEnvelope + evidencia (page/bbox/crop)
        ▼
NormalizedEvent + raw_row + confidence
        │
        ▼
DedupMatcher → FinancialMovement + MovementSource
        │
        ▼
AccountResolver → account_id / account_destino_id / kind
        │
        ▼
DecisionOrchestrator (reglas → Jev) → Classification
```

**Cambios clave:**

- `BaseParser.detect()` debe recibir un `FileProbe`, no solo 6 líneas de texto. Los PDFs son binarios.
- `parse()` no puede exigir 1 evento por fila: un PDF puede tener una fila raw por página/bloque y varios eventos. Cambiar el contrato a `ParsedUnit[]` con `raw_ref`, `page`, `line_start`, `line_end`.
- Guardar el fichero con su extensión original: `data/files/<sha256><ext>`; `source_files.mime_type`, `page_count`, `account_id`.
- Importación transaccional: crear `source_file` en `uploaded`, pasar a `parsing`, `parsed` o `failed`; nunca dejar una fila a medias.
- Importación idempotente: mismo `(source, file_hash)` devuelve 200 con `duplicate=true` y el `source_file_id`, no 409. `force/reprocess` debe re-parsear de verdad, no devolver el resultado anterior.
- Importación en background para PDFs/OCR: tabla `jobs` persistente con `type`, `payload`, `status`, `progress`, `attempts`, `locked_at`; worker que reanuda tras reinicio. Para CSV pequeños, síncrono.
- Límites: tamaño máximo, páginas máximas, timeout, validación de PDF, protección ante PDFs escaneados sin texto.

**Parsers PDF recomendados:**

- **Trade Republic statement** (`docs/legacy_docs/Extracto...pdf`): texto extraíble con `pdfplumber`; las filas tienen fecha, descripción multi-línea, importe y balance corriente. La dirección se puede derivar del delta de balance (`balance_i - balance_{i-1}`), lo que además valida la extracción. Reconciliar suma de importes con `saldo_final - saldo_inicial`; si no cuadra, marcar `needs_review`.
- **Revolut statement** (`extracto_cuenta_revolut.pdf`): tabla con fecha transacción, fecha valor, descripción, dinero saliente/entrante y saldo. Parsear por tabla/regex; reconciliar balance.
- **TR valores/cripto**: no son movimientos, son posiciones. Parsear a `position_snapshots` de apertura (no a `financial_movements`).
- **Fallback genérico**: `DocumentIntakeAgent` (§5.9) con texto/tablas + visión local, JSON Schema (`page`, `saldo_inicial`, `saldo_final`, `transacciones[]`), evidencia y `needs_review`. Solo si no hay parser determinista.
- **Escaneados**: detección de PDF sin texto → OCR + visión local; si no se puede, `needs_review` con motivo. No fingir que se ha importado.
- **Recibos/facturas**: imagen o PDF → OCR/visión extrae merchant, fecha, total, impuestos; el decisor categoriza; se intenta casar con una transacción de tarjeta existente y se guarda como evidencia.

### 5.2 Deduplicación idempotente

Diseño propuesto:

1. **L0 fichero**: `UNIQUE(source, file_hash)`. Re-subida = 200 idempotente, no error.
2. **L1 broker ID**: `source_txn_id` con índice único por fuente; si existe, se reutiliza el movimiento y se crea `movement_source`. Nunca se usa fingerprint si hay `transaction_id`.
3. **L2 sin ID estable**: `dedup_key` (hash de cuenta + fecha valor + dirección + importe + moneda + merchant normalizado + descripción normalizada) + `occurrence_index` dentro del fichero. El matching consume candidatos 1:1: si hay 2 movimientos existentes con la misma clave y llegan 2 filas, se enlazan ambos; si llega una tercera, se crea nuevo y se marca candidato. Esto preserva las repeticiones legítimas.
4. **L3 parecidos**: bloqueo por fecha ±3 días, mismo importe absoluto y mismo kind; scoring de merchant (Jaccard) y contraparte. Solo cola `dedup_candidates`; **nunca merge automático**.
5. **L4 repeticiones legítimas**: resolución “distinto” persistente; el par no vuelve a preguntarse.
6. **Transferencias internas**: no son duplicados; se enlazan con `movement_links` (`internal_transfer`). Un outgoing de TR y un incoming de Revolut del mismo importe/fecha son dos movimientos, no uno.

**Invariantes testeables:**

- Importar dos veces el mismo CSV: 0 nuevos, 585 vistos, 0 clasificaciones nuevas, 0 cambios de estado.
- Dos filas idénticas con distinto `transaction_id`: 2 movimientos.
- Dos filas idénticas sin ID: 2 movimientos; reimport: 2 vistos, 0 nuevos.
- CSV + PDF solapados: los movimientos comunes se enlazan; los exclusivos del PDF se crean; los candidatos dudosos van a la cola.
- `Σ amount` por mes = `Σ CSV.amount` por mes.

### 5.4 Capa de decisión: Jev + OpenCode Go

**Decisión: solo Jev como decisor.** Laya queda descartado: requiere GPU para una latencia buena y su checkpoint base es casi azar en typed-decisions zero-shot (0.362; el fine-tuned llega a 0.766). Sin GPU no compensa el coste de operación. Jev es API, no necesita hardware local y devuelve decisiones tipadas con `confidence` calibrada.

**Modelos documentales: OpenCode Go desde Python, sin agente embebido.** Usamos la suscripción Go (`oc_sk_...`) para llamar directamente a la Inference API. No montamos `opencode serve` ni un sidecar Node. El backend Python habla HTTP con OpenCode:

| Pieza | Dónde se ejecuta | Qué usar |
|---|---|---|
| Decisor | TypeSafe API | `POST /v1/systemone`, `model="jev-latest"`, `TYPESAFE_API_KEY` |
| Modelo documental default | OpenCode Go | **`deepseek-v4.1-flash`**, 0 días, mucho más rango de uso |
| Fallback | OpenCode Go | `glm-5.3-flash`, `qwen3.8-flash`, `mimo-v2.6-flash` o `gpt-6-luna` |

**Endpoints de Go relevantes:**

- **DeepSeek V4.1 Flash (default):** `POST https://opencode.ai/inference/go/openai/v1/chat/completions` (texto e imagen; **no PDF directo**: renderizar páginas a PNG o extraer texto con `pdfplumber`).
- GLM-5.3-Flash, Qwen3.8 Flash, MiMo: mismo endpoint Chat Completions.
- GPT-6 Luna: `POST https://opencode.ai/inference/go/openai/v1/responses` (Responses API; acepta texto, imagen y PDF). Solo fallback.
- Claude Haiku 5.5: `https://opencode.ai/inference/go/anthropic/v1/messages`.
- Gemini 4 Argon: `https://opencode.ai/inference/go/google/v1beta/models/gemini-4-argon:generateContent`.

**Retención:** DeepSeek V4.1 Flash, GLM-5.3-Flash, Qwen3.8 Flash y MiMo tienen **0 días**. GPT-6 Luna retiene 30 días y solo se usa como fallback.

**Límites de Go (imagen de la suscripción):** DeepSeek V4.1 Flash **$100/mes**, 43.330 req/5 h, 86.670/semana. GPT-6 Luna **$15/mes**, 4.230 req/5 h. Por eso DeepSeek es el default: más rango y coste efectivo dentro de la suscripción. El cliente leerá `usage.opencode.allowance` y hará fallback si queda poco.

**Headers recomendados por Go:** `User-Agent: financial-tools/0.1`, `x-opencode-session: <uuid>` estable por import/documento, `Authorization: Bearer oc_sk_...`. No usar un user-agent genérico de SDK.

**Si Go falla o se agota:** fallback a otro modelo Go (GLM/Qwen/MiMo; GPT-6 Luna si hace falta PDF directo). **No hay OpenRouter.** El `DecisionProvider`/`DocumentModelProvider` abstrae el modelo para no acoplar el pipeline.

**Contrato del decisor:**

```json
{
  "state": {
    "merchant": "AHORRAMAS",
    "description": "Compra tarjeta 09/01",
    "amount": -38.06,
    "currency": "EUR",
    "mcc": "5411",
    "broker_type": "CASH_CARD_TRANSACTION",
    "account": "Trade Republic",
    "counterparty": null,
    "rule_hits": ["MCC 5411 → Alimentación"],
    "precedents": [{"merchant": "AHORRAMAS", "categoria": "Alimentación"}]
  },
  "model": "jev-latest",
  "questions": {
    "kind": {"type": "choice", "instructions": "...", "criteria": {"gasto": "...", "...": "..."}},
    "categoria": {"type": "choice", "instructions": "...", "criteria": {"Alimentación": "...", "...": "..."}},
    "es_transferencia_interna": {"type": "noul", "instructions": "..."},
    "requiere_revision": {"type": "noul", "instructions": "..."}
  }
}
```

La respuesta trae `choice`, `probabilities`, `confidence` y `noul`. La API es síncrona y rápida (70–500 ms), pero el contrato documentado es **un `state` por llamada** con varias preguntas en paralelo; no asumir batch de estados. Para 500 movimientos: reglas/memoria primero, cache por `state_hash` y Jev solo para el subconjunto dudoso; si se necesita procesar muchos, paralelizar con límite de concurrencia.

```python
class DecisionProvider(Protocol):
    name: str
    def ask(self, state: dict, questions: dict, *, timeout: float = 5) -> dict: ...

class JevProvider:        # POST https://api.typesafe.ai/v1/systemone
class OpenCodeGoClient:   # /inference/go/openai/v1/{responses,chat/completions}

class DecisionOrchestrator:
    def decide(self, state, questions, *, risk: str):
        # 1. Reglas y memoria ya resueltas en código
        # 2. Jev para el resto
        # 3. si confidence < umbral o risk=alto → needs_review con probabilidades
        ...
```

**State pequeño y redactado.** Merchant, descripción limpia, importe, moneda, MCC, broker_type, cuenta, contraparte, reglas que han casado y precedentes. Nunca el PDF ni la imagen. Esto mantiene la latencia, el coste y la privacidad bajo control.

**Preguntas atómicas, no una pregunta gigante.** Siguiendo la recomendación de TypeSafe:

1. `kind` (12 opciones) para validar el tipo canónico.
2. `categoria` (14 opciones) condicionada al `kind`; si el catálogo crece, jerarquía grupo → categoría.
3. `subtipo` (5 opciones) solo si aplica.
4. `es_transferencia_interna` (noul) con evidencia de cuenta/contraparte.
5. `es_duplicado_probable` (noul) solo para pares candidatos.
6. `requiere_revision` (noul) para el gate humano.

Jev admite hasta 255 opciones, así que no hace falta jerarquía por límite técnico; sí por calidad semántica y por explicabilidad.

**Cascada de decisión:**

```
1. Broker facts (kind, activo, dividendo, interés, cashback, aporte)
   → categoría por defecto, origen='broker', confianza=1.0
2. Reglas deterministas (cuenta propia, MCC, merchant, broker_type)
   → origen='rule', confianza=0.99, auto-aprobar configurable
3. Memoria exacta / embeddings (precedentes)
   → origen='memory'/'embedding'
4. Jev (decisiones tipadas) para el resto
   → origen='decider', modelo='jev:...'
5. LLM generativo solo para evidencia/extracción o explicación
6. Humano si Jev da baja confianza o hay desacuerdo con reglas
```

**Umbrales por riesgo (empezar conservador):**

| Decisión | Auto-aceptar | Revisar | Nunca automático |
|---|---:|---:|---|
| Categoría de gasto/ingreso | `confidence ≥ 0.90` y margen top-2 ≥ 0.15 | `< 0.75` | — |
| Transferencia interna | `P ≥ 0.95` + IBAN/patrón coincide | `0.80–0.95` | Solo por nombre si hay duda |
| Duplicado | `P ≥ 0.90` + misma fecha/importe | `0.70–0.90` | Nunca borrar; solo enlazar o encolar |
| Documento válido | `P ≥ 0.95` + conciliación OK | `0.80–0.95` | Documento no soportado |

La `confidence` de Jev es una función de la distribución; aun así, validar los umbrales con el golden set. No convertir una probabilidad alta en auto-aprobación si la conciliación de balance o la evidencia fallan. Ojo: las respuestas `noul` no traen `confidence`; usar la probabilidad directamente (p. ej. `p ≥ 0.9` para sí, `p ≤ 0.1` para no) o `|2p-1|` como confianza.

**Bucle de acuerdo LLM + decisor:**

```
agente documental (OpenCode Go multimodal + tools)
  → propone hechos + evidencia + incertidumbres
decisor (Jev)
  → responde preguntas atómicas con probabilidades
código
  → compara con reglas y con la propuesta del LLM
  → si acuerdo y confianza alta: aceptar
  → si desacuerdo o confianza media: pedir evidencia adicional al agente
    (crop de página, línea raw, movimiento similar, patrón de cuenta)
  → repetir máximo 2 iteraciones
  → si sigue sin acuerdo: revisión humana con evidencia
```

El decisor no "habla" con el LLM; el orquestador es código determinista. Esto evita bucles infinitos, prompt injection y costes descontrolados. Cada iteración se guarda en `decision_runs`/`agent_runs` para auditoría.

**Evaluación:**

- Golden set: las 152 decisiones de usuario ya heredadas, más etiquetas nuevas de documentos (tipo, banco, fila, importe, categoría).
- Métricas: accuracy, macro-F1, coverage, ECE (calibración), latencia, coste, tasa de desacuerdo, tasa de revisión humana.
- Jev zero-shot con el schema completo; probar variantes de `instructions`/`criteria` y few-shot en el `state`.
- Document agent: comparar GPT-6 Luna vs DeepSeek V4.1 Flash vs GLM-5.3-Flash en el mismo golden set de documentos (extracción, JSON válido, coste, latencia).
- Guardar `modelo`, `prompt_version`, `decision_run_id`, `confidence`, `probabilities` en la clasificación; `llm_calls` para coste/allowance.

**Privacidad:** a Jev solo se envía el `state` estructurado y redactado (merchant, MCC, importe, descripción limpia), nunca el PDF ni la imagen. El agente documental usa DeepSeek V4.1 Flash (**0 días**) por defecto; GPT-6 Luna (30 días) solo si se necesita PDF directo. Redactar IBAN/nombres antes de enviar páginas o texto.

**Riesgos específicos:** Jev está en early access y es una API cerrada; abstraer `DecisionProvider` para no acoplar. La latencia (70–500 ms) se multiplica si se llama por fila: cachear por `state_hash` y usar Jev solo para el subconjunto dudoso. OpenCode Go está pensado para tráfico de coding y monitoriza abuso; usar user-agent propio, `x-opencode-session`, volumen bajo y fallback a otro modelo Go. Controlar límites mensuales/semanales de Go.

### 5.8 Infraestructura, seguridad y observabilidad

**PostgreSQL-first (decidido).** El despliegue real es PostgreSQL; SQLite queda solo como conveniencia de desarrollo/tests forenses.

- `DATABASE_URL=postgresql+psycopg://user:pass@host:5432/financial`; `psycopg[binary]` v3, no `psycopg2`.
- Pool: `pool_size=10`, `max_overflow=20`, `pool_pre_ping=True`, `pool_recycle=1800`; sin `StaticPool`.
- Migraciones: `alembic upgrade head` en entrypoint; fallar rápido si la revisión no coincide. `init_db()`/`create_all` solo tests.
- Esquema: `NUMERIC(18,4)` para dinero, `DATE` para fecha valor, `JSONB` para `raw_rows.payload`, `TIMESTAMPTZ` para timestamps, índices parciales/expresiones donde aporten.
- Nada de SQL específico de SQLite ni de superusuario: `datetime('now')`, `PRAGMA`, `INSERT OR REPLACE`, `SET session_replication_role` (el script de reset actual puede fallar en Postgres gestionado). Revisar `memory.py`, `scripts/reset_v2.py`, `db/session.py`; usar `TRUNCATE ... CASCADE` en orden o borrado por dependencias.
- Migración/reconciliación de datos: si PG no tiene la verdad, `scripts/migrate_sqlite_to_postgres.py` con dry-run, conteos y checksums; si ya la tiene, reconciliar por `transaction_id`/conteos antes de tocar nada.
- Tests de integración contra PostgreSQL real (testcontainers/CI service), no SQLite, para detectar diferencias.
- Backups: `pg_dump`/`pg_basebackup`, WAL archiving, retención y test de restore; nunca backup dentro del repo.
- Observabilidad: `pg_stat_statements`, slow query log, conexiones, locks; alertas de pool agotado.

- **Docker**: PostgreSQL actual vía `DATABASE_URL` externa por env/secret (sin IP/credenciales hardcodeadas; compose opcional para dev), backend con healthcheck, instalar dependencias desde `pyproject` (incluye `pdfplumber`/`openpyxl`, `typesafe-sdk`, `psycopg[binary]`, `argon2-cffi`), copiar `scripts/`, `DATA_DIR=/data/files`, migrar al arrancar, healthcheck `/healthz`.
- **Secretos**: API key por env o cifrada; no devolverla nunca; `SECRET_KEY` para cifrado.
- **Auth**: login propio single-user con Argon2id, sesiones opacas en PostgreSQL, cookie `HttpOnly`/`Secure`/`SameSite=Lax`, CSRF y rate limit; ver §5.11. No basta basic auth si hay UI.
- **Privacidad**: `.gitignore` para DB/CSV/PDF; redacción de IBAN/BIC/literales antes de OpenCode Go/Jev; DeepSeek/GLM/Qwen (0 días) por defecto; GPT-6 Luna (30 días) solo si hace falta PDF directo; a Jev solo state redactado; aviso claro de qué sale a cada API.
- **Logs**: JSON estructurado, request ID, duración, import_id, job_id; sin volcar descripciones completas.
- **Métricas**: imports/min, % auto-clasificado, correcciones, latencia LLM, tokens/coste, cola pendiente, duplicados.
- **Health**: DB, revisión Alembic, storage escribible, LLM configurado, worker activo.

### 5.9 Agente documental con OpenCode Go + decisor Jev

La idea de “que la IA valide y parsee cualquier documento” es viable, pero **no debe ser un agente autónomo sin límites**. La forma robusta es un **orquestador determinista con herramientas** y un modelo multimodal vía **OpenCode Go** solo para lo que las herramientas no resuelven. El agente produce un `DocumentEnvelope`; Jev decide sobre hechos estructurados. Jev no ve el PDF ni la imagen.

> **Decisión 2026-10-31 — agente-first:** se implementa el agente de extracción
> como camino principal para cualquier banco/formato, con validación
> determinista y el parser de Trade Republic solo como fallback temporal. El
> diseño de implementación, contrato, fases y criterios de aceptación está en
> [`AGENTIC_INGESTION.md`](./AGENTIC_INGESTION.md). Cuando el agente supere el
> golden set, se retiran el registry y el parser actual.

**Por qué híbrido y no “multimodal lo hace todo”:** un parser determinista para un CSV/PDF conocido es más rápido, más barato y más preciso que una llamada de visión; el modelo multimodal aporta valor en layouts desconocidos, escaneados y recibos. Un agente libre por cada subida multiplica coste/latencia, es difícil de testear, no da confianza calibrada y abre la puerta a prompt injection y tool calls erróneos. El agente debe ser un **gatekeeper acotado**: siempre valida, pero solo usa visión/LLM cuando la validación determinista no basta.

**Flujo completo:**

```
upload (CSV/PDF/XLSX/imagen/email)
   │
   ▼
FileProbe determinista (mime, magic bytes, tamaño, páginas)
   │
   ▼
DocumentIntakeAgent (código + tools + multimodal OpenCode Go)
   ├── extract_text / extract_tables / render_page / ocr
   ├── detect_bank / detect_account / detect_period
   ├── parse_rows / normalize_fields
   ├── reconcile_balance
   ├── match_existing_movements / detect_duplicates
   └── save_evidence (crop, bbox, page)
   │
   ▼
DocumentEnvelope (hechos + evidencia + issues + confianza)
   │
   ▼
Normalizer determinista → NormalizedEvent
   │
   ▼
Dedup + AccountResolver
   │
   ▼
DecisionOrchestrator (Jev)
   ├── kind / categoria / subtipo
   ├── es_transferencia_interna
   ├── es_duplicado_probable
   └── requiere_revision
   │
   ▼
Agreement loop (máx. 2 iteraciones)
   ├── acuerdo + confianza alta → FinancialMovement
   ├── desacuerdo / confianza media → pedir evidencia al agente
   └── sigue dudoso → revisión humana con evidencia
```

**Herramientas del agente (allowlist, sin shell ni red):**

| Tool | Función |
|---|---|
| `probe_file` | MIME, extensión, magic bytes, tamaño, páginas, cifrado |
| `extract_text` | Texto por página (`pdfplumber`/`pypdf`) |
| `extract_tables` | Tablas y celdas con coordenadas |
| `render_page` | PNG de página/crop para el modelo multimodal y la UI |
| `ocr_image` | OCR opcional para escaneados/recibos |
| `read_spreadsheet` | XLSX/CSV con mapping de cabeceras |
| `detect_layout` | Multimodal: columnas, filas, cabeceras, ruido |
| `detect_bank` | Heurística + Jev: banco, tipo de documento |
| `parse_rows` | Extracción determinista o asistida |
| `reconcile_balance` | Suma de importes vs saldo inicial/final |
| `find_existing_movements` | Matching con movimientos ya importados |
| `save_evidence` | Crop + bbox + página + hash en `document_evidence` |
| `ask_decider` | Preguntas tipadas a Jev |
| `finish_envelope` | Cierra con `needs_review` o `ok` |

El modelo multimodal **no ejecuta herramientas libremente**: el orquestador decide qué tool llamar según el estado. El modelo solo analiza imágenes/páginas ambiguas y devuelve JSON validado. Esto evita prompt injection y tool calls arbitrarios.

**Estructura de código propuesta:**

```
src/ai/

  jev.py             # cliente /v1/systemone (typesafe-sdk o httpx)
  document_agent.py  # orquestador + tools + DocumentEnvelope
  decision.py        # preguntas atómicas, umbrales, cache
  schemas.py         # Pydantic: DocumentEnvelope, DecisionRequest/Response
  tools/             # probe, extract, render, ocr, balance, evidence
```

- `opencode_go.py`: base `https://opencode.ai/inference/go`, `OPENCODE_API_KEY`, `x-opencode-session`, `User-Agent: financial-tools/0.1`, Chat Completions para DeepSeek/GLM/Qwen y Responses para GPT-6 Luna; `response_format` JSON Schema; leer `usage.opencode.allowance`.
- `jev.py`: `POST https://api.typesafe.ai/v1/systemone`, `TYPESAFE_API_KEY`, `model="jev-latest"`, `typesafe-sdk` si simplifica; timeout y retries.
- Todos con tests de contrato y mocks; nunca llamar a la API real en tests unitarios.

**`DocumentEnvelope` (contrato estable):**

```json
{

  "period": {"start": "2026-01-01", "end": "2026-06-30"},
  "balances": {"opening": 11375.93, "closing": 11220.04, "currency": "EUR"},
  "units": [

  ],
```

**Validaciones que hace el código (no el modelo):**

- Tipo de documento soportado y banco detectado.
- Cuenta/IBAN identificados o creación explícita.
- Periodo y moneda.
- Parseo de fechas/importes con `Decimal`.

- Filas duplicadas y solapamiento con imports previos.
- Esquema JSON y rangos válidos.
- Evidencia presente para cada fila (`page`, `bbox` o `raw_text`).
- Si algo falla: `needs_review`, nunca auto-aprobar.

### 5.10 OpenCode Go API directa (decidido, sin agente embebido)

**No se usa OpenCode como agente.** No hay `opencode serve`, ni sidecar Node/Bun, ni sesiones/permisos de OpenCode. El backend Python llama directamente a la Inference API de OpenCode Go con `httpx`/OpenAI SDK.

**Cliente Python (`src/ai/opencode_go.py`):**

```python
class OpenCodeGoClient:
    base = "https://opencode.ai/inference/go"
    def __init__(self, api_key: str): ...
    def responses(self, model, input, schema, session_id): ...
    def chat(self, model, messages, schema, session_id): ...
```

- GPT-6 Luna: `POST /openai/v1/responses`.
- DeepSeek V4.1 Flash / GLM-5.3-Flash / Qwen3.8 Flash / MiMo: `POST /openai/v1/chat/completions`.
- Claude Haiku 5.5: `POST /anthropic/v1/messages`.
- Gemini 4 Argon: `POST /google/v1beta/models/gemini-4-argon:generateContent`.
- Headers: `Authorization: Bearer oc_sk_...`, `User-Agent: financial-tools/0.1`, `x-opencode-session: <uuid por import/documento>`.
- Structured output: JSON Schema en `response_format` (Chat Completions) o `text.format` (Responses); validar con Pydantic y reintentar si no cumple.
- Leer `usage.opencode.allowance` y `billing_source='go'` para controlar límites; guardar en `llm_calls`.
- Errores: 401 key inválida, 402 sin saldo (no debería con Go), 403 modelo no permitido, 429 rate limit, 5xx; retry con backoff y fallback.

**Modelos y retención:** DeepSeek V4.1 Flash, GLM-5.3-Flash, Qwen3.8 Flash y MiMo 0 días; GPT-6 Luna 30 días. Default DeepSeek; GPT-6 Luna solo para PDF directo/calidad.

**Uso previsto:** Go está pensado para tráfico de agentes de coding y monitoriza abuso. Este uso es de bajo volumen (documentos personales), con user-agent propio y sesión estable; si OpenCode lo bloquea, se cae a otro modelo Go.

### 5.11 Autenticación (single-user, session cookie)

La app se expone con login. Para un solo usuario no hace falta OAuth ni multi-tenant; sí una auth sólida y simple.

**Backend:**

- Tablas `users` y `sessions`; seed del admin desde `ADMIN_EMAIL` + `ADMIN_PASSWORD_HASH` (Argon2id) o script CLI `scripts/set_password.py`.
- `POST /api/v3/auth/login` (email+password), `POST /logout`, `GET /me`, `POST /change-password`. Sin 2FA por ahora.
- Cookie de sesión opaca `__Host-ft_session` en prod (`HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/`, sin Domain); en dev `ft_session` sin `Secure`. Token aleatorio de 32 bytes; guardar solo SHA-256 en `sessions`.
- Expiración 7 días con rotación; “cerrar todas las sesiones”.
- CSRF: cookie `ft_csrf` legible + header `X-CSRF-Token` en POST/PATCH/DELETE; validar en middleware. `SameSite=Lax` como segunda capa.
- Rate limit de login por IP+email (5/min, bloqueo progresivo), registrar intentos en `login_attempts`; no revelar si el email existe.
- Argon2id para passwords; nunca loguear passwords/tokens; comparación timing-safe.
- `require_user` dependency en todos los routers excepto `/healthz` y `/auth/login`; proteger `/docs` o desactivarlo en prod.
- CORS same-origin; quitar `localhost:3000` de producción.
- Sesiones en PostgreSQL, no en memoria: revocables y consistentes entre workers.

**Frontend:**

- `/login` con split-screen, email/password, error genérico, loading y “recordarme” (extiende sesión).
- `middleware.ts` comprueba presencia de cookie y redirige a `/login`; la API valida de verdad.
- `AuthProvider`/`useMe` con TanStack Query; 401 global → limpiar cache y redirigir.
- Menú de usuario: cambiar password, cerrar sesión, cerrar todas las sesiones.
- Logout con `POST` + CSRF, no un GET.

**Dependencias:** `argon2-cffi`, `slowapi` o rate limit propio, `itsdangerous` solo si se firman cookies auxiliares.

**Secretos:** `SESSION_SECRET`, `ADMIN_EMAIL`, `ADMIN_PASSWORD_HASH`, `TYPESAFE_API_KEY`, `OPENCODE_API_KEY` por env/secret manager; nunca en `app_config` ni en el repo.

**Modelo de datos:**

```sql
users(id, email UNIQUE, password_hash, role,
      created_at, last_login_at, disabled)
sessions(id, user_id FK, token_hash UNIQUE, created_at, expires_at,
         last_seen_at, ip, user_agent, revoked_at)
login_attempts(id, email, ip, ok, created_at)
```

**Criterio de salida:** sin sesión, todo `/api/v3/*` devuelve 401; login/logout/CSRF/rate-limit testeados; cookie no accesible por JS; sesión revocada deja de valer inmediatamente.

## 9. Riesgos y decisiones abiertas

| Riesgo | Impacto | Mitigación |
|---|---|---|
| `transaction_id` no estable entre exportaciones | Duplicados L1 | L2 con clave + consumo 1:1; monitorizar `movement_seen_count` |
| PDFs de otros bancos con estructuras distintas | Parser roto | Adaptadores por banco + agente multimodal + evidencia + revisión |
| PDFs escaneados | Sin texto | OCR + visión + `needs_review`; no auto-importar |
| PostgreSQL actual con drift/datos distintos | Divergencia | Inventario, `pg_dump`, dry-run y reconciliación antes de migrar |
| Jev early access / API cerrada | Dependencia y coste | Abstracción `DecisionProvider`; baseline OpenCode Go; no acoplar |
| Límites de OpenCode Go (5h/semanal/mensual) | Ingesta bloqueada | Leer `usage.opencode.allowance`, fallback a otro modelo Go, avisar en UI |
| Retención Go: GPT-6 Luna 30 días | Privacidad | Default DeepSeek 0 días; GPT-6 Luna solo para PDF directo |
| Go pensado para coding | Bloqueo por uso | Volumen bajo, user-agent propio, `x-opencode-session`, fallback Go |
| Fallback Go no configurado | Caída si el modelo falla | Cliente abstracto + modelos Go alternativos + test de failover |
| Auth mal configurada | Acceso no autorizado | Argon2id, cookie HttpOnly/Secure, CSRF, rate limit, tests |
| Agente alucina filas/importes | Datos corruptos | Evidencia obligatoria, conciliación, JSON Schema, revisión; nunca auto-aprobar sin balance |
| Prompt injection en documentos | Tool calls maliciosos | Orquestador determinista, allowlist, sin shell/red; documento = datos |
| Complejidad del agente | Retraso del proyecto | Fases: determinista → Jev → agente; no empezar por el agente autónomo |
| Rehacer UI de golpe | Regresión | Construir en `/new` o repo aparte, validar con Playwright y cambiar el tráfico cuando esté verde |
| Datos personales en Git | Privacidad | `.gitignore`, `git rm --cached`, revisar historia |
